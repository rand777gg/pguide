# 01 · 工程结构与技术栈

## 1. 仓库整体结构

```
pguide/
├── PGuide-Back/          后端微服务集群（Spring Boot 2.6 + Cloud Alibaba + Nacos）
├── PGuide-Front/         前端（Vue3 monorepo + 历史 Vue2 工程）
├── PGuide-Manage/        运营后台（RuoYi 3.8.6 二次开发，单体）
├── dev-manual/           本目录：开发规范
├── docker/               Docker 编排与初始化 SQL
└── compose.yaml          本地一键环境入口
```

三个后端部分是**管理面 / 业务面分离**：

- **PGuide-Back**：面向学生的业务面，走 Nacos 注册 + 网关统一鉴权
- **PGuide-Manage**：面向老师/管理员的运维后台，**不走网关**，
  用 Druid 多数据源直连 4 个业务库

前端两套都对接 PGuide-Back 的网关（默认 `localhost:666`）。

### 为什么必须上 TypeScript

不是为了"显得现代"，是因为这个项目已经**因为缺类型吃过亏**：

- `@pguide/api` 里 `fetchSubjectTree()` 的返回结构是**邻接表**
  （`data[0]` 是一级，`data[subjectId]` 是二级），老代码在组件里手工拼，
  没人知道返回值长这样。加上类型后 `SubjectAdjacencyList` 一眼看懂。
- 后端 `UserInfoVo` 有 8 个字段，老工程靠 `res.data.xxx` 猜字段名。
- 环境变量：老工程 `.env.production` 里漏了 `VUE_APP_AUTH_API`，
  运行时是 `undefined`，静默失败。现在 `ImportMetaEnv` 声明了每个变量，
  写错名字编译期就报错。
- `ProjectCreatedVo` 的 `typeLevel` 只能是 `'free' | 'unfree'`，
  用联合类型收窄后，随手写字符串会被拦下。

**规则：`any` 一律不许用。** 实在绕不过去时用 `unknown` + 类型守卫，
并写注释说明为什么。

## 3. 前端目录结构

```
PGuide-Front/
├── pnpm-workspace.yaml      workspace 定义
├── package.json             根脚本（dev / build / lint / test）
├── tsconfig.base.json       共享 TS 基础配置
├── .npmrc                   registry + 严格依赖
│
├── packages/
│   ├── shared/              @pguide/shared —— 通用类型、常量、纯函数
│   │   └── src/
│   │       ├── constants/   http-status.ts / storage-keys.ts
│   │       ├── types/       user.ts（UserInfoVo / LoginBody / CaptchaResult）
│   │       ├── utils/       storage.ts（localStorage 封装）
│   │       └── index.ts
│   │
│   └── api/                 @pguide/api —— axios 客户端 + 各业务域接口
│       └── src/
│           ├── config.ts    configureApi()，由 app 注入环境
│           ├── http.ts      两个 axios 实例 + 拦截器 + ApiError
│           ├── modules/     auth.ts / cms.ts / subject.ts / mms.ts
│           └── index.ts
│
└── apps/
    └── match/               @pguide/match —— 组队中心
        └── src/
            ├── api/         setup.ts（把环境注入 @pguide/api）
            ├── components/  可复用的展示组件
            ├── router/      路由表 + 守卫
            ├── services/    视图模型层（组合多个 API、做数据转换）
            ├── stores/      Pinia store
            ├── styles/      全局样式 + 设计令牌
            ├── views/       页面（与路由一一对应）
            └── main.ts
```

### 分层职责（违规最容易出在这里）

| 层 | 允许做什么 | 不允许做什么 |
|---|---|---|
| `views/` | 组合组件、调用 `services/`、处理用户交互 | 直接 `import axios`、写复杂数据转换 |
| `services/` | 组合多个 API、把后端结构转成 UI 需要的结构、兜底 mock | 碰 DOM、碰路由、存组件状态 |
| `components/` | 通过 props 接收数据、通过 emit 抛事件 | 自己发请求、直接读 store（除非是明确的容器组件） |
| `stores/` | 跨页面共享的状态与它对应的 action | 存只有单个组件用的临时状态 |
| `packages/api/` | 定义接口、类型、拦截器 | import 任何 app 的东西（router/store） |

**判断标准**：`packages/` 里的代码如果删掉某个 app 就不能用了，说明分层错了。

### 为什么 `services/` 要有单独一层

看 `apps/match/src/services/project.ts` 就明白了：
热门项目、需求市场这两个列表，**后端目前没有接口**，只能返回占位数据。

如果按老工程的做法把假数据直接写在组件里，将来后端接口好了，
要在两个组件里分别改。现在包一层 service，届时只改这一个文件，
组件一行都不用动。这不是过度设计，是为已知的待办留的接口。

## 4. 包引用规则

```ts
// ✅ 跨包引用走包名
import { STORAGE_KEYS } from '@pguide/shared'
import { mmsApi, ApiError } from '@pguide/api'

// ✅ app 内部引用走 @ 别名（映射到 src/）
import { useUserStore } from '@/stores/user'

// ❌ 不许跨包用相对路径穿透
import { STORAGE_KEYS } from '../../../packages/shared/src/constants/storage-keys'

// ❌ 不许从包内部深层路径 import（packages 只暴露 exports 里的入口）
import { ApiError } from '@pguide/api/src/http'
```

`packages/*` 直接以 **TS 源码**形式被消费（`exports` 指向 `src/index.ts`），
由 Vite 负责转译，不单独产出 `dist`。这样改共享代码不需要先 build，
调试时断点也能直接落在源码上。

## 5. 后端约定的几个硬约束

前端写接口时要知道这些（详细见 [04-API层与数据流](./04-API层与数据流.md)）：

1. **统一响应体**：`{ code, message, data }`，业务失败时 HTTP 仍然是 200，
   必须看 `body.code`。成功是 `200` / `202`。
2. **自定义错误码**：`307` 表示"需要跳转统一鉴权中心"，不是 HTTP 307。
3. **token 走自定义请求头 `token`**，不是 `Authorization`，也没有 `Bearer` 前缀。
4. **网关路由前缀**：`/api/auth/**`、`/api/mms/**`、`/api/cms/**`、
   `/api/user/**`、`/api/index/info/**`。
