# 08 · 质量门禁

## 1. 三条命令

```bash
cd PGuide-Front

pnpm lint          # ESLint，0 warning 才算通过
pnpm type-check    # vue-tsc，覆盖 .vue 模板里的类型
pnpm test          # Vitest
```

一次性跑：

```bash
pnpm lint && pnpm type-check && pnpm test
```

**提交前必须全绿。** 不允许"先提交，回头再修"。

---

## 2. 各道门禁拦什么

| 门禁 | 工具 | 拦得住的问题 |
|---|---|---|
| 格式 | Prettier | 缩进、引号、分号、行宽 —— 不再靠人 review |
| 静态检查 | ESLint 9（flat config） | 未使用变量、`==`、`any`、`console.log`、Vue 特有陷阱 |
| 类型 | vue-tsc | 字段名写错、类型不匹配、环境变量名拼错、模板里引用不存在的属性 |
| 测试 | Vitest | 逻辑回归（当前覆盖较少，见下） |

### 为什么类型检查必须包含 `.vue`

只跑 `tsc` 检查不到模板里的错误。`vue-tsc` 会检查：

```vue
<template>
  <!-- ❌ 如果 SubjectTreeNode 没有 subjectTitle 字段，vue-tsc 会报错 -->
  <span>{{ node.subjectTitle }}</span>
</template>
```

老工程没有这一层，模板里写了不存在的字段要到运行时打开控制台才发现。

## 3. ESLint 配置要点

配置在 `apps/match/eslint.config.js`（ESLint 9 的 flat config 格式）。

关键规则：

| 规则 | 级别 | 原因 |
|---|---|---|
| `@typescript-eslint/no-explicit-any` | warn | 见 [02-编码规范](./02-编码规范.md) |
| `@typescript-eslint/consistent-type-imports` | error | 配合 `verbatimModuleSyntax` |
| `eqeqeq` | error | 老代码混用 `==` / `===` |
| `vue/multi-word-component-names` | off | 页面组件用目录组织，允许单词名 |
| `no-console` | warn（允许 warn/error） | 防止 `console.log` 混进提交 |

**不要用 `// eslint-disable` 绕过规则。** 确实需要时：

```ts
// eslint-disable-next-line @typescript-eslint/no-explicit-any -- 第三方 SDK 无类型定义
const sdk = (window as any).SomeSDK
```

必须写 `--` 后面的原因说明，reviewer 会检查。

## 4. 测试策略

### 现状：测试很少

这是实际情况，不粉饰。当前只有脚手架级别的配置，
业务测试需要逐步补。**不要因为"测试少"就把测试门槛抬得很高，
导致没人愿意写第一个测试。**

### 优先级：先测纯逻辑

最容易写、收益最高的顺序：

1. **纯函数 / 数据转换**（无 DOM、无网络）
   - `buildSubjectTree()` —— 邻接表转嵌套树
   - `loadSubjectTree()` 里 `subjectLevel === 1` 的兜底分支
   - `readStorage` / `writeStorage` 的异常分支

2. **Pinia store 的 action**
   - `redeemTokenCode()`：成功 / 失败 / 无 code 三条路径
   - 一次性 code 是否被正确清除

3. **组件交互**（用 `@vue/test-utils`）
   - `SubjectCascade`：点击一级节点后二三级列是否正确更新
   - `CreatedGroup`：切换 `typeLevel` 后 `type` 是否回退到合法值

4. **API 层**（用 axios mock 或 MSW）
   - `code=307` 时是否触发了跳转回调
   - 401 时是否清了 token

### 示例

```ts
// apps/match/src/services/__tests__/subject.spec.ts
import { describe, expect, it, vi } from 'vitest'
import { buildSubjectTree } from '@pguide/api'

describe('buildSubjectTree', () => {
  it('把邻接表转成嵌套树', () => {
    const adjacency = {
      '0': [{ subjectId: 1, subjectName: '数学建模', subjectLevel: 1 }],
      '1': [{ subjectId: 4, subjectName: '算法', subjectLevel: 2 }],
    }
    const tree = buildSubjectTree(adjacency)
    expect(tree).toHaveLength(1)
    expect(tree[0]!.children[0]!.subjectName).toBe('算法')
  })

  it('没有 0 号根节点时返回空数组', () => {
    expect(buildSubjectTree({})).toEqual([])
  })
})
```

### 不要去测什么

- 第三方库的行为（Element Plus 的按钮点得动不需要你验证）
- 纯样式
- 快照测试（除了极少数稳定结构，快照只会带来无意义的 diff）

## 5. 提交前自查清单

```bash
# 1. 编译与检查
pnpm lint && pnpm type-check && pnpm test

# 2. 本地跑一下，改动涉及的页面手动点一遍
pnpm dev

# 3. 看清暂存区里到底有什么
git status
git diff --cached --stat
```

逐条确认：

- [ ] lint 0 warning
- [ ] type-check 通过
- [ ] 相关测试通过（有的话）
- [ ] 没有留下 `console.log` / `debugger`
- [ ] 没有注释掉的大段代码（要删就删，git 里有历史）
- [ ] 没有提交 `node_modules` / `dist` / 密钥
- [ ] 新增的 TODO 写了责任方（`TODO(后端)` / `TODO(前端)`）
- [ ] 改动了接口/契约时，同步更新了 `dev-manual/` 里对应文档

## 6. CI（未来）

当前还没有 CI。建议的最小流水线：

```yaml
# .github/workflows/frontend.yml
name: frontend

on:
  pull_request:
    paths: ['PGuide-Front/**', 'dev-manual/**']

jobs:
  check:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: PGuide-Front
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 12 }
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
          cache-dependency-path: PGuide-Front/pnpm-lock.yaml
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm type-check
      - run: pnpm test
      - run: pnpm build
```

**落地 CI 时注意**：`pnpm install --frozen-lockfile` 会走
`minimumReleaseAge` 策略校验，所以锁定版本（如 `sass-embedded@1.104.0`）
必须写死在 `package.json` 里，否则 CI 上可能因为策略拒绝而失败
（详见 `PGuide-Front/pnpm-workspace.yaml` 里的注释）。
