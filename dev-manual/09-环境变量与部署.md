# 09 · 环境变量与部署

## 1. 命名规则的硬变化

| | 老工程（Vue CLI） | 新工程（Vite） |
|---|---|---|
| 前缀 | `VUE_APP_` | **`VITE_`** |
| 访问方式 | `process.env.VUE_APP_XXX` | **`import.meta.env.VITE_XXX`** |
| 类型声明 | 无 | `env.d.ts` 里的 `ImportMetaEnv` |

**只有 `VITE_` 开头的变量会被注入前端产物。** 写成 `VUE_APP_` 或别的名字，
取到的是 `undefined`，而且**不会报错**。

老工程就是栽在这里：`.env.production` 里只定义了 `VUE_APP_BASE_API`，
漏了 `VUE_APP_AUTH_API` 和 `VUE_APP_IF_OPEN_AUTH`，
导致生产环境的鉴权和路由守卫全部静默失效。

新工程的对策：`env.d.ts` 声明了每个变量，**拼错名字 `vue-tsc` 会直接报错**。

```ts
// apps/match/env.d.ts
interface ImportMetaEnv {
  readonly VITE_APP_TITLE: string
  readonly VITE_API_BASE_URL: string
  readonly VITE_AUTH_API_BASE_URL: string
  readonly VITE_SELF_URL: string
  readonly VITE_PROXY_TARGET?: string
  readonly VITE_AUTH_GUARD: string
}
```

---

## 2. 变量清单

| 变量 | 开发值 | 生产值 | 说明 |
|---|---|---|---|
| `VITE_APP_TITLE` | 项导组队中心 | 同左 | 页面标题 |
| `VITE_API_BASE_URL` | `/api` | `/prod-api` | 业务接口基地址 |
| `VITE_AUTH_API_BASE_URL` | `/api` | `/prod-api` | 鉴权中心基地址 |
| `VITE_SELF_URL` | `http://localhost:4000/` | 部署域名 | 鉴权中心登录后回跳地址，**必须是绝对地址** |
| `VITE_PROXY_TARGET` | `http://localhost:666` | 不使用 | 仅 dev：Vite 代理目标（网关） |
| `VITE_AUTH_GUARD` | `false` | `true` | 是否启用登录守卫 |

**每个环境都必须定义全部变量。** 不是"用不到就不写"——
`VITE_AUTH_GUARD` 在老工程里就是因为在 production 里没定义，
`undefined === 'true'` 恒为 false，守卫等于没有。

## 3. 开发环境为什么用代理而不是绝对地址

老工程 `.env.development`：

```
VUE_APP_BASE_API=http://localhost:666/api
```

这是**跨域请求**，能不能通取决于网关的 CORS 配置（`GlobalCorsConfig`）。
配置一旦漏了某个头，前端就报 CORS 错误，而后端同学可能根本不知道。

新工程：

```
VITE_API_BASE_URL=/api
VITE_PROXY_TARGET=http://localhost:666
```

```ts
// vite.config.ts
server: {
  proxy: {
    '/api': { target: env.VITE_PROXY_TARGET, changeOrigin: true },
  },
}
```

浏览器发的是**同源请求**，由 dev server 转发到网关。
**从根上不存在跨域**，也就不用维护 CORS 白名单。

网关的路由前缀本身就是 `/api/auth/**`、`/api/mms/**`，
所以代理**不需要 rewrite**，转发过去路径刚好对得上。

## 4. 构建

```bash
cd PGuide-Front

pnpm build              # 全部 app
pnpm build:match        # 只构建组队中心
```

`build` 脚本会**并行**跑类型检查和打包：

```json
"build": "pnpm -r --filter \"./apps/*\" build"
```

### ⚠️ Windows 上的单引号陷阱（真实踩过）

上面这条命令里的 `"./apps/*"` **必须用双引号**。

一开始写的是单引号 `'./apps/*'`：

```json
"build": "pnpm -r --filter './apps/*' build"
```

结果在 Windows 上 **`pnpm build` 什么都不做，还返回退出码 0**。
原因是 pnpm 在 Windows 上通过 **cmd.exe** 执行 package.json 里的脚本，
而 cmd.exe **不把单引号当引号** —— 它会连同引号一起传下去，
filter 变成字面量 `'./apps/*'`，匹配不到任何包，于是静默跳过。

更坑的是：在 PowerShell 里手动敲同一条命令**是正常的**（PowerShell 认单引号），
所以调试时对着命令行验证会得出"没问题"的错误结论。

**规则：package.json 的 scripts 里引用路径/通配符一律用双引号**，
双引号在 cmd.exe 和 POSIX shell 里都是合法引号。

验证方法（不要只看退出码）：

```bash
rm -rf apps/*/dist
pnpm build
ls -d apps/*/dist        # 每个 app 都应该有产物
```

## 5. 部署（nginx）

前端产物是纯静态文件，需要一个 nginx 做两件事：
**SPA 回退** + **转发 `/prod-api` 到网关**。

```nginx
server {
    listen       80;
    server_name  _;
    root         /usr/share/nginx/html;
    index        index.html;

    # 1. SPA 回退。新工程用 history 模式，直接访问 /user 这种路径时
    #    nginx 找不到对应文件，必须回退到 index.html 交给前端路由。
    #    老工程用的是 hash 模式，不需要这一条 —— 这是迁移后必须新增的配置。
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 2. 静态资源长缓存（文件名带内容 hash，可以放心缓存）
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 3. index.html 不缓存，否则发版后用户拿不到新版本
    location = /index.html {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }

    # 4. 业务接口转发到网关
    location /prod-api/ {
        proxy_pass http://pguide-gateway:666/api/;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

**注意 `proxy_pass` 末尾的 `/api/`**：把 `/prod-api/xxx` 重写成 `/api/xxx`，
与网关的路由前缀对齐。

## 6. 多环境

| 文件 | 何时生效 | 用途 |
|---|---|---|
| `.env` | 所有模式 | 所有环境共享的默认值（本项目不用） |
| `.env.development` | `vite` / `pnpm dev` | 本地开发 |
| `.env.production` | `vite build` | 生产构建 |

优先级：`.env.[mode].local` > `.env.[mode]` > `.env.local` > `.env`

**`.env.*.local` 一律不提交**（已在 `.gitignore` 里），
用来放个人机器的覆盖值。

新增环境（如测试环境）时：加 `.env.staging`，
并在 `package.json` 加 `"build:staging": "vite build --mode staging"`。

**别忘了新文件里要把所有变量都定义上**（见第 2 节的警告）。

## 7. 前端要不要进 Docker

当前**没有**为前端做 Dockerfile。原因：

1. 前端产物是静态文件，开发期用 `pnpm dev` 的 HMR 效率远高于容器
2. 打镜像需要把 `node_modules` 放进构建上下文（几百 MB），收益不明显

要部署时，推荐在 CI 里 `pnpm build`，然后把 `dist/` 拷进 nginx 镜像：

```dockerfile
FROM nginx:alpine
COPY dist/ /usr/share/nginx/html/
COPY nginx.conf /etc/nginx/conf.d/default.conf
```

**注意**：不要用 `node:xx` 跑构建再 `nginx` 托管的双阶段里
把整个 `PGuide-Front` 拷进去 —— 仓库里有三个老 Vue2 工程各自的
`node_modules`，会拖慢构建。见根目录 `.dockerignore` 的说明。

## 8. 检查清单

新增或修改环境变量时：

- [ ] 变量名以 `VITE_` 开头
- [ ] 已在 `env.d.ts` 的 `ImportMetaEnv` 里声明
- [ ] **所有** `.env.*` 文件里都定义了（或用代码里的默认值兜底）
- [ ] 没有把密钥写进 `.env.development` / `.env.production`
- [ ] 如果只有开发环境需要，命名上标注清楚（如 `VITE_PROXY_TARGET`）
- [ ] 更新了本文档的变量清单
