# 06 · 鉴权与会话

这个项目的鉴权是本仓库里**最容易踩坑**的部分。老实现有三处硬伤，
本文档把正确契约固化下来。

---

## 1. 三个组成部分

| 组件 | 位置 | 职责 |
|---|---|---|
| 网关 `GlobalJWTFilter` | `pguide-gateway` :666 | 校验 token，把 `*:<userType>` 写进请求头 `SysAuthKey` |
| 鉴权中心 `pguide-auth` | :888（经网关 `/api/auth/**`） | 发 token、维护 Redis 会话、提供统一登录页 |
| 业务服务 `@UserAuth` 切面 | 各 provider | 按 `SysAuthKey` 做细粒度权限判断 |

前端只跟网关打交道。

---

## 2. token 怎么放、怎么带

### 存储位置：`localStorage`，唯一来源

```ts
// ✅ 统一走 @pguide/shared 的封装
import { STORAGE_KEYS, readStorage, writeStorage } from '@pguide/shared'
readStorage<string>(STORAGE_KEYS.TOKEN)
```

**key 名**：`PGUIDE_TOKEN`（定义在 `STORAGE_KEYS`，不要手写字符串）

> ⚠️ 老工程的坑：`utils/request.js` 读的是 `localStorage['token']`，
> 而 `utils/auth.js` 写的是 `sessionStorage['token']` —— 两套存储不一致，
> 导致登录状态随机失效。**新代码只允许走 `STORAGE_KEYS`。**

### 请求头：`token`，不是 `Authorization`

```http
GET /api/mms/create/test HTTP/1.1
token: eyJhbGciOiJIUzI1NiJ9...
```

网关 `GlobalJWTFilter` 读的 header 名就是 `token`，
**没有 `Bearer` 前缀**（这是老工程的约定，不要"顺手改成标准写法"）。
注入逻辑在 `packages/api/src/http.ts` 的请求拦截器里，业务代码不用管。

## 3. 统一鉴权中心（SSO）完整流程

```
① 前端发现无 token
   └─ 调 GET /auth/authCenter/redirect?sendUrl=<本应用地址>
        ↓
② 后端返回 code=307 + { redirectUrl, sendUrl }
   └─ redirectUrl 是鉴权中心登录页地址
        ↓
③ 前端生成一次性 code（uuid）
   ├─ 存 localStorage['PGUIDE_TOKEN_CODE']
   └─ 整页跳转 <redirectUrl>redirect?code=<uuid>&sendUrl=<urlencoded>
      （redirectUrl 是后端配置的 pguide.server.path.authPage = http://localhost:99/）
        ↓
④ 用户在鉴权中心登录，鉴权中心把 token 写进后端 Redis
   （key 是那个 uuid，有效期 1 分钟）
        ↓
⑤ 鉴权中心带上 code 回跳到 sendUrl（= 业务应用）
        ↓
⑥ 业务应用启动时读 localStorage 里的 uuid
   └─ 调 GET /auth/authCenter/tokenEx?tokenCode=<uuid> 换到真正的 token
        ↓
⑦ 存 token → 调 GET /auth/userinfo/vo 拿 UserInfoVo → 进入正常流程
```

### 关键点：第 ⑥ 步靠 localStorage，不靠 URL 参数

**这一点非常重要。** 老版 auth-ui 用 `new URL(...).searchParams` 解析
`#/redirect?code=xxx&sendUrl=yyy`，但 `searchParams` 读的是 `#` **之前**的部分，
所以它实际**取不到 code** —— 那段子系统登录判断从来没生效过。

整条链路之所以还能跑通，是因为第 ③ 步把 uuid 存进了 localStorage，
第 ⑥ 步是从 localStorage 读的，跟 URL 参数无关。

**现状（已修复）**：`apps/auth` 已经重写，
解析逻辑统一收在 `@pguide/api` 的 `parseAuthRedirectParams()` 里，
它同时支持两种形式：

| 形式 | 例子 | 说明 |
|---|---|---|
| 新（history 路由） | `http://localhost:99/redirect?code=..&sendUrl=..` | 现在的生成方式 |
| 老（hash 路由） | `http://localhost:99/#/redirect?code=..&sendUrl=..` | 兼容历史链接 |

生成侧用 `buildAuthRedirectUrl()`，解析侧用 `parseAuthRedirectParams()`，
两侧共用一份实现，不会各写各的。

这个协议有单元测试守着（`packages/api/src/__tests__/auth-redirect.spec.ts`），
其中一条专门断言"用原生 `searchParams` 解析老形式会失败"，
防止有人把它改回去。

### 一次性 code 必须消费掉

```ts
async function redeemTokenCode(): Promise<boolean> {
  const code = readStorage<string>(STORAGE_KEYS.TOKEN_CODE)
  if (!code) return false
  try {
    const token = await authApi.exchangeToken(code)
    applyToken(token)
    return true
  } finally {
    // 无论成败都要删 —— 后端那边只保留 1 分钟，留着只会让下次流程混乱
    removeStorage(STORAGE_KEYS.TOKEN_CODE)
  }
}
```

## 4. 路由守卫

```ts
router.beforeEach(async (to) => {
  const userStore = useUserStore()

  // 回跳落地：先尝试兑换 token
  if (to.name === 'authCallback' || !userStore.isAuthenticated) {
    await userStore.ensureSession()
  }

  if (to.name === 'authCallback') {
    return userStore.isAuthenticated ? { name: 'home' } : true
  }

  // 需要登录的页面
  if (import.meta.env.VITE_AUTH_GUARD === 'true' && to.meta.requiresAuth && !userStore.isAuthenticated) {
    return { name: 'forbidden', query: { redirect: to.fullPath } }
  }

  return true
})
```

**必须用返回值写法。** 老工程是这样的：

```js
// ❌ next('/403') 之后又无条件 next()，重定向被作废，守卫等于没有
router.beforeEach((to, from, next) => {
  if (!token && to.path !== '/403' && IF_OPEN_AUTH === 'true') {
    next({ path: '/403' })
  }
  next()
})
```

另外一个坑：老工程判断条件里的 `process.env.VUE_APP_IF_OPEN_AUTH`
在 `.env.production` / `.env.test` 里**根本没定义**，运行时是 `undefined`，
所以生产环境守卫也是失效的。

新工程用 `VITE_AUTH_GUARD`，**三个 env 文件里都显式定义**。

## 5. 401 处理

会话失效（网关返回 401）时：

1. `packages/api` 清掉本地 token
2. 通过 `onUnauthorized` 回调通知应用
3. 应用清空 store 用户态 + 跳 `/403`

```ts
// apps/match/src/api/setup.ts
configureApi({
  onUnauthorized: () => {
    useUserStore().reset()
    void router.push({ name: 'forbidden' })
  },
})
```

**为什么用回调而不是在 api 包里直接 import router**：
api 包是跨 app 复用的，不能依赖某个 app 的路由实例。见
[04-API层与数据流](./04-API层与数据流.md) 第 6 节。

## 6. 开发期跳过鉴权

`.env.development` 里 `VITE_AUTH_GUARD = false`，
这样不跑鉴权中心也能直接看页面。

**这只影响路由守卫，不影响接口鉴权** —— 需要 token 的接口仍然会 401。
要完整联调，还是得起全套后端：

```bash
docker compose --profile full --profile back --profile manage up -d
```

## 7. 安全检查清单

新增涉及鉴权的代码时，逐条确认：

- [ ] token 只存在 `localStorage`，key 用 `STORAGE_KEYS.TOKEN`
- [ ] 请求头是 `token` 且不带 `Bearer`
- [ ] 一次性 code 用后即删（`finally` 里删）
- [ ] 路由守卫用返回值写法，没有 `next()` 后面再写 `next()`
- [ ] 需要登录的页面在 `meta` 里标了 `requiresAuth: true`
- [ ] 401 会清 token 并跳登录，不会陷入死循环
- [ ] 重定向的 `sendUrl` 做了 `encodeURIComponent`
- [ ] 没有把 token 写进 URL（老工程 `LoginController.loginOther` 会
      `redirect:xxx?token=...`，这一点在重写后端时要改掉）

## 8. 网关白名单与「哪些接口不需要登录」

网关的白名单在 `pguide-gateway/sc-gateway/src/main/resources/bootstrap.yml`：

```yaml
pguide:
  gateway:
    authentication:
      url: /api/auth/login,/api/auth/**,/api/cms/subject/tree
```

命中的路径由 `GlobalJWTFilter` 直接放行，并注入权限头 `*:*`。
**其余所有路径都要求 token**，没有 token 直接返回 401
（响应体是 `{"status":"401","errorMsg":"登录异常"}`，不是标准 JsonResult）。

### 匹配规则是 Ant 通配，不是前缀比较

`GlobalJWTFilter` 把配置值按逗号切分后，逐个交给
`PathUtil.checkAuthKeyValue()` → hutool 的 `AntPathMatcher`。
所以 `**` / `*` 都生效，例如 `/api/cms/subject/**` 能匹配
`/api/cms/subject/tree`。

### 什么接口该进白名单

判断标准只有一条：**用户在登录之前需不需要看到它？**

需要 → 进来。典型的是浏览型、字典型只读接口。
不需要 → 别进来，最小权限。

当前白名单里的三条及理由：

| 路径 | 理由 |
|---|---|
| `/api/auth/login` | 登录本身当然不能要求先登录 |
| `/api/auth/**` | 验证码、鉴权中心跳转、token 换取 |
| `/api/cms/subject/tree` | 学科分类树，首页登录前就要展示的公开字典数据 |

### 案例：学科树曾经被拦（已修复）

`apps/match` 首页的学科分类区块依赖 `GET /api/cms/subject/tree`，
但它原先不在白名单里，未登录访问直接 401，首页显示「加载失败」。

修复方式就是把该路径加进白名单。注意这里用的是**精确路径**而不是
`/api/cms/**` —— 同一个 controller 前缀下将来可能有需要登录的接口，
放开整个前缀是过度授权。

验证时除了确认目标接口放行，**更要确认没被误放行**：

```bash
# 应该 200
curl.exe -s -o NUL -w "%{http_code}\n" "http://localhost:666/api/cms/subject/tree"
# 应该仍然是 401（同一个 /api/cms 前缀下的其他接口）
curl.exe -s -o NUL -w "%{http_code}\n" "http://localhost:666/api/cms/cptinfo/list"
# 应该仍然是 401
curl.exe -s -o NUL -w "%{http_code}\n" "http://localhost:666/api/mms/create/test"
```

改动白名单要重建网关镜像（配置打在 jar 里）：

```bash
docker compose --profile back build gateway
docker compose --profile back up -d gateway
```
